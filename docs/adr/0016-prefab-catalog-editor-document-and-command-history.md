# ADR-0016: Prefabs come from a generated catalog; the editor edits a document made of commands

- **Status:** accepted
- **Date:** 2026-09-06
- **Deciders:** project maintainers

## Context

Two gaps blocked the world editor (spec §13, §14, phase 4 of §51).

**Nothing said what a prefab is.** `EntityDefinition.prefab` has always been an
id — `"pine_tree_01"` in the example world — pointing at nothing. There was no
format, no file, no check: `pnpm validate` happily accepted an entity whose
prefab did not exist and never could. At the same time the repository gained 438
placeable assets through the import of ADR-0015, each already carrying its path,
visibility, placeholder and measured bounds in `assets/manifest.json`. Writing a
prefab for each of them by hand would be 438 opportunities to mistype a path.

**Nothing said what an edit is.** `@wov/editor-core` contained
`createEmptyWorld` and nothing else, while `apps/editor` is a React shell around
a Babylon.js viewport. Placement, selection, delete, duplicate, transform and
undo/redo (spec §14: Q/W/E/R/F, Delete, Ctrl+D, Ctrl+Z, Ctrl+Y) all change world
data. Written inside React components they would be untestable without a
browser, and the rule they must obey — the result is always a valid
`WorldDefinition` — would live in event handlers.

## Decision

**1. A prefab catalog is a content format.** `PrefabDefinition` and
`PrefabCatalog` live in `@wov/world-schema`; catalogs are files in
`content/prefabs/*.json` with their own `schemaVersion`. A prefab carries `id`,
`name`, `asset`, `visibility`, `placeholder` (required for a private asset,
forbidden for a public one), `category` and optionally `bounds` and
`defaultScale`. Prefab ids are unique across **all** catalogs, because an entity
names an id with no catalog attached.

**2. The bulk catalog is generated from the manifest and committed.**
`pnpm generate:prefabs` writes `content/prefabs/imported.json`: one prefab per
placeable asset (`mesh`, `prefab`, `terrain`; not textures, not placeholders),
with the id, name and category derived from the asset path by pure functions.
`content/prefabs/base.json` stays hand-written.

**3. `pnpm validate:content` checks the references.** Catalogs are validated,
prefab ids must be unique across catalogs, and every `prefab` an entity names
must exist.

**4. `@wov/editor-core` owns an editor document made of commands.** An
`EditorDocument` is `{ world, selection, activeZoneId, dirty }`; a change is an
`EditorCommand` value; `applyCommand` is a pure function returning a new
document plus the command that undoes it; the history stores those two commands
per step. Nothing in the package imports Babylon.js or React.

## Alternatives considered

| Alternative                                                            | Why not                                                                                                                                                                                                             |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Let the editor read `assets/manifest.json` directly                    | The manifest says which files exist, not what is placeable, how it is called or which category it belongs to. Prefabs are authored data that outlives an import; the manifest is regenerated by the asset pipeline. |
| Generate `imported.json` at build or run time instead of committing it | The game would then depend on the manifest, which ADR-0012 forbids, and a clone without an asset store would see no prefabs. A committed file is also reviewable in a diff.                                         |
| Hand-write all 438 prefabs                                             | 438 chances to mistype a path, and no way to notice when the manifest changes.                                                                                                                                      |
| Import `AssetPathSchema` from `@wov/asset-system`                      | Content validation would then need the asset pipeline, and `@wov/world-schema` would gain a dependency it does not need. The rule is short and closed; both copies carry a note saying they change together.        |
| Undo by keeping a stack of world snapshots                             | Simple, but every step copies the whole world, and the editor is meant to hold a large hand-crafted world. Commands with inverses cost two small objects per step.                                                  |
| Put selection and commands in React state inside `apps/editor`         | Untestable without a browser, and it would put world rules into event handlers — exactly what spec §10 separates.                                                                                                   |

## Consequences

**Positive.** An entity's `prefab` now resolves to something, and a typo fails in
CI instead of at load time. The editor gets a full model to build on — place,
delete, duplicate, transform, rename, undo, redo — that is covered by tests
without a browser. Undo is not a special case in the UI: `execute`, `undo` and
`redo` are pure functions of one state value.

**Negative.** `content/prefabs/imported.json` is a 4 000-line generated file in
the repository. It is committed deliberately (see the alternatives), it is
regenerated with one command, and a test compares it with what the current
manifest produces, so drift is caught rather than debated. The asset path rule
exists twice; both copies carry a comment, a boundary rule enforces the reason,
and they must change in one commit.

**Not a world generator.** Generating a catalog is not procedural world
generation (agent rule 16): it produces the _vocabulary_ of things that can be
placed, never a placement. Where anything stands is authored in
`content/worlds/`, by a person, through the commands in `@wov/editor-core`, and
persisted as data (agent rule 17).

**Follow-ups.**

- `apps/editor` binds the keyboard defaults of spec §14 to these commands, and a
  smoke test asserts a visible marker for each new surface.
- The importer files the Kenney barrel as `environment` because its file name
  carries no prop marker; a curated entry in `base.json` corrects such cases.
- `dungeon` is a category no asset carries yet; it is claimed for the modular kit
  of spec §20.
- Prefab overrides per entity (spec §19, "safe propagation") are not part of this
  ADR. When they arrive, `EntityDefinition` changes and the world format version
  is bumped with a migration.
